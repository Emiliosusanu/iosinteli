## What changed

Build 380 lacked Chrome's immediate Bookshelf price-change path. Build 381 scans the current explicitly Live physical rows, checks account/ASIN/setup identity and explicit currency, persists the detailed retry before writing, and writes the safe primary US price/economics before the detail gate attempt. Unchanged prices do not generate a fast write. No full-detail capture timestamp is advanced by this path. Only successful detailed capture clears the retry.

The shared helper refuses to reuse a cached royalty rate across the US paperback $9.99 tier boundary, an inconsistent historical rate, unknown cost, foreign/VAT economics or ambiguous identity. It preserves verified stored economics and leaves the detailed capture pending. This is a safe US/USD fast path, not a claim that EUR/CAD/AUD royalties can be inferred from a Bookshelf price alone. Native prices, costs, royalties and break-even values for every marketplace still come from the detailed calculator capture.

The actual `syncKdpPaperbackPricing` function is exercised through cached fresh detail + changed Bookshelf price → fast write and persisted dirty state → blocked gate → next wake retry despite freshness → unlocked USD/CAD calculator response → pending queue cleared. Pure tests cover changed/unchanged prices, Live-only selection, exact identity, ISBN, tier crossing, and persist-before-write failure handling.

## Refund distinction and October 9 follow-up

A local PostgreSQL/PGlite reproduction of the actual deployed migrations confirms a limitation: an accepted day with USD 6.53, one order and zero KENP cannot automatically become zero royalties/orders/KENP. The full-refund-shaped update raises `KDP_DESTRUCTIVE_CORRECTION_QUARANTINED` and retains the prior day. A partial correction with changed activity is accepted. This demonstrates data protection, but is not evidence that all legitimate refunds are supported. No production refund or data replacement was attempted.

Required correction design (not implemented by this follow-up): preserve accepted and candidate snapshots separately; record account/date/marketplace/currency/source completeness and capture provenance; authenticate the source/account; distinguish explicit zero from missing/failed reports; accept a material decrease through validated refund/return evidence reconciled at the relevant book/market/day scope, or through an audited administrator recovery when the source cannot expose sufficient evidence. Require atomic replacement of facts/books/totals and retain a recoverable prior revision. Repeating the same zero response alone must not authorize replacement, and a client-supplied `refund=true` must not bypass quarantine. The current report replay does not preserve refund evidence sufficient to implement that acceptance automatically.

Official KDP prior-month reports expose Units Refunded and Net Units Sold: https://kdp.amazon.com/en_US/help/topic/G200641190 . This does not prove that the current daily estimator endpoints expose equivalent evidence or that refunds revise the original order date.
